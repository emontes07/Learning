What you will build

An agent called Infrastructure Lookup Agent. A member of the Infrastructure team types a plain-English question in Microsoft Teams — "Is ENR-LT-1234 still enabled in AD?" — and the agent:

  • Works out what kind of lookup is being asked for (computer name, user name, or asset ID).
  • Validates the input against a strict allowlist pattern before anything executes.
  • Calls one fixed, approved PowerShell function on an authorized on-premises machine.
  • Receives structured JSON back — never free text, never a screen scrape.
  • Reports one of six explicit outcomes: found, not found, multiple matches, invalid input, unauthorized, or runner unavailable.

Learning objectives

Objective 1

Understand where code actually executes

The language model never runs PowerShell. It selects a tool and passes typed parameters. A deterministic runner executes the script. You will see this boundary in the activity map.

Objective 2

Wire Copilot Studio to an on-premises resource

Agent → agent flow → desktop flow → PowerShell → Active Directory, with typed inputs and a JSON contract at every hop. You will build the agent flow yourself and see the runner hop demonstrated — the contract is identical either way.

Objective 3

Design a safe tool, not a script runner

Learn why "an agent that runs any PowerShell" is an unacceptable design, and how a fixed function with an output allowlist gives you the same demo with none of the risk.

Objective 4

Leave with a reusable pattern

The same scaffold covers the ENR server inventory use case, the Tote SKU lookup, and any other on-premises read-only scenario in the portfolio.

01

Is this even possible? The straight answer

Yes
A Copilot Studio agent can run a PowerShell script against on-premises Active Directory — but not directly, and not an arbitrary one.

Copilot Studio has no "run PowerShell" capability and the language model executes nothing. What the agent can do is call a deterministic tool. That tool chain — agent flow → desktop flow → Run PowerShell script action on a registered on-premises machine — is a fully supported, documented Microsoft path. That is what we will build.

Separating the two questions

The askThe realityVerdict
"An agent that can run a PowerShell script" — one known, approved script with defined inputs and outputs. Fully supported. The agent passes typed parameters to a flow; the flow triggers a desktop flow on a machine that has the AD module; the script returns JSON. Build it
"An agent that can run any PowerShell script" — the user (or the model) supplies the command text. Technically possible and categorically unsafe. It turns a chat box into remote code execution against a domain controller, with the model as the only gatekeeper. No amount of prompt engineering makes this an acceptable control. Do not build
Guardrail — the non-negotiable design rule

The agent reasons; controlled tools execute. The script text is fixed and version-controlled on the runner. The agent may only supply parameters, and only parameters that pass an allowlist regular expression. If a participant asks "can it just run whatever I type?", the answer is no — and this section explains why in language an infrastructure audience respects.

What we were actually asking — in plain language

Question decoded

"Authentication model and user permissions"

Translation: whose account does the script run under, and who is allowed to ask?

Those are two different things, and mixing them up is how these projects go wrong.

  • Execution identity — the Windows / AD account the PowerShell runs as. In our design this is one dedicated read-only service account, not the person asking. Everyone's query runs with the same permissions.
  • Access control — who can talk to the agent at all. Because everyone shares one execution identity, this is your only real authorization boundary. It is enforced by sharing the agent with a specific Entra security group.

Decision: service account svc-copilot-adread (or equivalent), delegated read on one OU, no write rights anywhere. Agent shared with the Infrastructure security group only.

Question decoded

"Connector, API, or MCP endpoint availability"

Translation: is there already a door the agent can knock on, or do we have to build one?

  • Connector — a ready-made adapter Microsoft or a vendor ships (SQL, ServiceNow, SharePoint). Zero build.
  • API — an internal web service your team already runs. We wrap it in a custom connector. Small build.
  • MCP endpoint — a newer, agent-native way to expose tools. Best long-term, needs an endpoint to exist.

Decision: Active Directory has none of these on-premises today, so we use the fourth option — a runner: a machine you already own that executes the approved script and hands back JSON. Nothing to build, nothing to publish, no firewall change.

The five design decisions we are asking Energizer to confirm

  1. Fixed function, not a script runner One approved script with typed parameters. The agent can never supply command text. Security-critical
  2. Mock first, live second Participants build and prove the whole chain in mock mode. Live mode is switched on only after the facilitator has validated the runner separately. Because there is no AD test environment
  3. One dedicated read-only service account, scoped to one OU Not a domain admin, not the facilitator's account, not a personal account. Security-critical
  4. Output field allowlist The script returns only the fields on the list — computer name, DNS name, enabled, OS, last logon, OU. Nothing else can leak into a chat transcript. Data protection
  5. Six explicit outcome states Found, not found, multiple, invalid, unauthorized, runner unavailable. An unreachable runner must never be reported as "no results". Trust

Why hop 3 exists at all

A reasonable first question is why the agent does not simply call the desktop flow directly. It cannot: Microsoft documents that desktop flows are not supported as a tool in Copilot Studio. A desktop flow must be wrapped in a flow the agent can call, and that wrapper is hop 3.

That constraint turns out to be the best thing about this design. Because a wrapper is mandatory, there is a natural place to put validation that sits outside the runner and outside the model's reach — which is exactly what Lab 3 builds. The architecture is not defending against a limitation; it is using one.

It also means hop 4 is swappable. Anything that returns the agreed JSON contract can sit there: a registered runner, or — in this workshop — a fixture served by hop 3 itself. Hops 1, 2, 3, 5 and every guardrail are identical either way.

Which parts of this are production, and which part is standing in

It is easy to read the optional Lab 2 and conclude that the runner is the “real” build and the agent flow is a mock-up. That is the wrong way round, and the distinction matters when an infrastructure audience asks what they are actually reviewing.

Lab 1

Prepare the runner and the approved script

On the runner machine

This is the only file that will ever execute. It is fixed, parameterized and read-only. It runs in two modes — Mock against a local fixture, Live against the directory — and the differences between them are called out explicitly below.

  1. Create the folder structure

    On the runner machine, create C:\EnergizerAgent\ and restrict write access to administrators only. The service account needs read and execute on the script.

    PowerShell · run once as administrator
    New-Item -ItemType Directory -Path 'C:\EnergizerAgent' -Force
New-Item -ItemType Directory -Path 'C:\EnergizerAgent\logs' -Force

    Restrict write access on C:\EnergizerAgent\ to administrators. The service account needs read and execute on the script itself, and modify on the logs subfolder only. Writing its own audit trail is not a violation of “read-only” — read-only refers to Active Directory. If you skip this, the script still runs, the log stays empty, and the Lab 6 acceptance criteria fails for a permissions reason that looks exactly like a script bug.

  2. Save the approved lookup script

    Save the following as C:\EnergizerAgent\Get-EnrComputerLookup.ps1. Read it out loud with the room — every guardrail in it is deliberate.

    Get-EnrComputerLookup.ps1
    <#
    Get-EnrComputerLookup.ps1
    Fixed-purpose, READ-ONLY computer lookup for the Energizer Infrastructure agent.

    Contract : validated lookup type + value in  ->  one JSON document out.
    Rule     : this script never accepts, builds, or invokes arbitrary commands.
#>

[CmdletBinding()]
param(
    [Parameter(Mandatory)]
    [ValidateSet('computerName','userName','assetId')]
    [string] $LookupType,

    # Allowlist pattern. Anything with a space, semicolon, quote, pipe or
    # bracket is rejected before a single directory call is made.
    [Parameter(Mandatory)]
    [ValidatePattern('^[A-Za-z0-9._-]{1,64}$')]
    [string] $LookupValue,

    [ValidatePattern('^[A-Za-z0-9-]{1,40}$')]
    [string] $CorrelationId = [guid]::NewGuid().ToString(),

    [ValidateSet('Mock','Live')]
    [string] $Mode = 'Mock',

    [ValidateRange(1,25)]
    [int] $MaxResults = 5,

    # Live mode only. Scope every query to one approved OU.
    # PLACEHOLDER - this distinguished name is invented. Confirm the real DN
    # with IT Infrastructure before enabling Live mode. A wrong DN silently
    # returns notFound for machines that visibly exist.
    [string] $SearchBase = 'OU=Devices,DC=corp,DC=energizer,DC=local',

    [string] $MockDataPath = 'C:\EnergizerAgent\mock-devices.csv',
    [string] $LogPath      = 'C:\EnergizerAgent\logs\lookup.log'
)

$ErrorActionPreference = 'Stop'
$started = Get-Date

# Only these fields are ever allowed to leave the runner. This list is applied
# in New-Result below, so it is an enforced control and not a comment.
$AllowedFields = 'computerName','dnsHostName','enabled','operatingSystem',
                 'lastLogonDate','organizationalUnit'

function Write-AuditLine {
    param([string] $Status, [int] $Count)
    $line = '{0}|{1}|{2}|{3}|{4}|{5}' -f (Get-Date).ToUniversalTime().ToString('o'),
            $CorrelationId, $Mode, $LookupType, $Status, $Count
    Add-Content -Path $LogPath -Value $line -ErrorAction SilentlyContinue
}

function ConvertTo-SafeText {
    # Directory free-text fields are attacker-influenced. Strip control
    # characters and truncate before this text reaches a language model.
    param([string] $Value)
    if ([string]::IsNullOrWhiteSpace($Value)) { return $null }
    $clean = ($Value -replace '[\x00-\x1F\x7F]', ' ').Trim()
    if ($clean.Length -gt 200) { $clean = $clean.Substring(0,200) }
    return $clean
}

function New-Result {
    param($Row)
    $obj = [pscustomobject][ordered]@{
        computerName       = ConvertTo-SafeText $Row.computerName
        dnsHostName        = ConvertTo-SafeText $Row.dnsHostName
        enabled            = [bool]::Parse([string]$Row.enabled)
        operatingSystem    = ConvertTo-SafeText $Row.operatingSystem
        lastLogonDate      = ConvertTo-SafeText $Row.lastLogonDate
        organizationalUnit = ConvertTo-SafeText $Row.organizationalUnit
    }
    # The allowlist is the control, not a comment. Every result is filtered
    # through it, so adding a field here is a deliberate, reviewable change.
    $obj | Select-Object -Property $AllowedFields
}

function Write-Response {
    # $Message is deliberately untyped. Declaring it [string] would coerce
    # $null into an empty string and break the "message": null contract.
    param([string] $Status, $Results = @(), $Message = $null)
    $items = @($Results)
    Write-AuditLine -Status $Status -Count $items.Count
    $payload = [ordered]@{
        status        = $Status
        correlationId = $CorrelationId
        mode          = $Mode
        resultCount   = $items.Count
        results       = $items
        message       = $Message
        source        = if ($Mode -eq 'Live') { 'On-premises Active Directory (read-only)' }
                        else { 'Mock fixture file' }
        executedAt    = (Get-Date).ToUniversalTime().ToString('o')
        durationMs    = [int]((Get-Date) - $started).TotalMilliseconds
    }
    # Single-line JSON is what the desktop flow hands back to the cloud.
    Write-Output ($payload | ConvertTo-Json -Depth 6 -Compress)
}

try {
    $rows = @()

    if ($Mode -eq 'Mock') {
        if (-not (Test-Path $MockDataPath)) {
            Write-Response -Status 'runnerUnavailable' `
                           -Message 'Mock fixture file was not found on the runner.'
            return
        }
        $all = Import-Csv -Path $MockDataPath
        switch ($LookupType) {
            'computerName' { $rows = $all | Where-Object { $_.computerName -eq $LookupValue } }
            'userName'     { $rows = $all | Where-Object { $_.primaryUser -eq $LookupValue } }
            'assetId'      { $rows = $all | Where-Object { $_.assetId      -eq $LookupValue } }
        }
    }
    else {
        if (-not (Get-Module -ListAvailable -Name ActiveDirectory)) {
            Write-Response -Status 'runnerUnavailable' `
                           -Message 'The ActiveDirectory module is not installed on the runner.'
            return
        }
        Import-Module ActiveDirectory -ErrorAction Stop

        # ------------------------------------------------------------------
        # PLACEHOLDERS - confirm all three with IT Infrastructure before Live.
        #   1. $SearchBase is an invented distinguished name.
        #   2. assetId maps to employeeID. The attribute is valid on computer
        #      objects but is almost never populated on them.
        #   3. userName maps to ManagedBy, which holds a DISTINGUISHED NAME,
        #      not a username. This path will NOT reproduce the T2 result you
        #      saw in Mock mode. A real deployment needs Intune primary-user
        #      data or a CMDB.
        #
        # String-form filters are used deliberately. The script-block form,
        # -Filter { Name -eq $LookupValue }, is parsed by the AD provider and
        # is unreliable with variables. The string form is safe here because
        # $LookupValue already passed [ValidatePattern] and cannot contain a
        # quote.
        # ------------------------------------------------------------------
        $props = 'DNSHostName','Enabled','OperatingSystem','LastLogonDate','DistinguishedName'
        $found = switch ($LookupType) {
            'computerName' {
                Get-ADComputer -Filter "Name -eq '$LookupValue'" `
                    -SearchBase $SearchBase -Properties $props -ErrorAction Stop
            }
            'assetId' {
                # PLACEHOLDER attribute - see note above.
                Get-ADComputer -Filter "employeeID -eq '$LookupValue'" `
                    -SearchBase $SearchBase -Properties $props -ErrorAction Stop
            }
            'userName' {
                # PLACEHOLDER attribute - see note above.
                Get-ADComputer -Filter "ManagedBy -eq '$LookupValue'" `
                    -SearchBase $SearchBase -Properties $props -ErrorAction Stop
            }
        }

        $rows = $found | ForEach-Object {
            [pscustomobject]@{
                computerName       = $_.Name
                dnsHostName        = $_.DNSHostName
                enabled            = $_.Enabled
                operatingSystem    = $_.OperatingSystem
                lastLogonDate      = if ($_.LastLogonDate) { $_.LastLogonDate.ToUniversalTime().ToString('o') } else { $null }
                organizationalUnit = ($_.DistinguishedName -replace '^CN=[^,]+,', '')
            }
        }
    }

    $rows = @($rows)

    if     ($rows.Count -eq 0) { Write-Response -Status 'notFound' -Message 'No record matched the supplied value.' }
    elseif ($rows.Count -eq 1) { Write-Response -Status 'found'    -Results (New-Result $rows[0]) }
    else {
        $trimmed = $rows | Select-Object -First $MaxResults | ForEach-Object { New-Result $_ }
        Write-Response -Status 'multiple' -Results $trimmed `
            -Message ('{0} records matched. Showing the first {1}.' -f $rows.Count, @($trimmed).Count)
    }
}
catch [System.UnauthorizedAccessException] {
    Write-Response -Status 'unauthorized' -Message 'The lookup identity is not permitted to read that scope.'
}
catch {
    Write-Response -Status 'runnerUnavailable' `
        -Message ('Lookup failed on the runner: {0}' -f (ConvertTo-SafeText $_.Exception.Message))
}
    Guardrail — read these four lines back to the room

    [ValidateSet] on the lookup type, [ValidatePattern] on the value, $AllowedFields on the output, and -SearchBase on the query. Those four constructs are what turn "an agent that runs PowerShell" into something a security team will sign.

    Explain it this way

    The hotel room-service phone

    Before reading the code, give the room the picture. It lands faster than the syntax does.

    We are not building an agent that runs PowerShell. We are building an agent that can press one button, and that button always does the same safe thing. These four constructs are what nail the button down so that nobody — not the user, not the model — can turn it into something else.

    Think of a hotel room-service phone with four preset buttons. It cannot dial an outside line. It cannot reach another guest's room. It cannot ring the building's control room. You press “towels”, towels arrive. That is this design.

    “An agent that runs any PowerShell” is the opposite: a phone with a full keypad, wired directly into the control room. Same convenience for the guest. Completely different risk for the building. These four lines are what turn the keypad into four buttons.

    What each line actually stops

    Each construct closes a different axis of risk. Individually each looks small; together they bound the operation on every side.

    ConstructWhat it boundsWhat someone can no longer do
    [ValidateSet('computerName','userName','assetId')] The operation Invent a fourth thing for the script to do. The model may pick from a menu of three; it cannot describe a new behavior and talk the script into it.
    [ValidatePattern('^[A-Za-z0-9._-]{1,64}$')] The input Sneak a command in through the value. Any space, semicolon, quote, pipe or bracket is rejected, so the value cannot break out of being a parameter and become a command.
    $AllowedFields The output Dump a whole directory object into a Teams conversation. An AD record carries dozens of attributes; exactly six approved fields are allowed to leave the runner.
    -SearchBase 'OU=Devices,…' The scope Search the whole forest. Every query is pinned to one organizational unit, so the worst-case blast radius is one OU.

    Bounded operation, bounded input, bounded output, bounded scope. That is defense in depth expressed in four lines of code that anyone in the room can read in thirty seconds and verify with their own eyes — no forty-page security review required.

    The distinction this callout is really teaching: guidance versus enforcement

    The agent's instructions in Lab 4 — “never run commands”, “you are read-only” — are guidance. Guidance is a sign on a door. Most people obey a sign; a determined person, or a prompt-injection string, simply ignores it.

    These four constructs are enforcement. Enforcement is the lock on the door. It does not matter what anyone types, argues, or jailbreaks — deterministic code rejects it the same way every time.

    That is why the handbook asks you to read them aloud. An infrastructure audience does not want to hear that the AI was told not to do bad things. They want to see the lock. These four lines are small enough that they can read them themselves and believe it.

    The rule that follows from this

    Later in the session someone will ask: “Could we just add a parameter so it runs any filter we want?” It is a reasonable question and it deserves a prepared answer.

    That single change removes all four walls at once. The correct response is never to make this function generic — it is to build a second fixed button, with its own four bounds and its own review.

    Mock and Live do not behave identically — say this out loud

    Mock mode is the right call given there is no AD test environment, but the handbook should not imply parity that does not exist. Three known divergences:

    • userName reads primaryUser from the fixture, but ManagedBy in Live. ManagedBy holds a distinguished name, not a username, so the T2 disambiguation test passes in Mock and will fail in Live. A real deployment needs Intune primary-user data or a CMDB.
    • assetId reads a CSV column in Mock and the employeeID attribute in Live. That attribute is valid on computer objects but is almost never populated on them.
    • lastLogonDate derives from lastLogonTimestamp, which replicates on a delay of up to roughly 14 days. If the team is asking “is this device still in use?”, that latency is a material accuracy caveat, not a footnote.

    None of this blocks the workshop. All of it blocks Live mode until Section 11 is answered.

    Before you run this — execution policy

    If the first command fails with “running scripts is disabled on this system” and a PSSecurityException, PowerShell’s execution policy is blocking the file from loading. Nothing in the script has run, and nothing has reached Active Directory. Check what is in effect:

    PowerShell · check the effective policy
    Get-ExecutionPolicy -List

    Scopes are evaluated in order — MachinePolicy, UserPolicy, Process, CurrentUser, LocalMachine — and the most specific one that is set wins. Pick the fix that matches your situation:

    • For this console session only (reverts when the window closes, no elevation needed):
      Set-ExecutionPolicy Bypass -Scope Process -Force
    • For the runner machine, persistently (survives reboots, still no elevation needed — this is the one to use if the same machine runs Lab 2):
      Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
    • If MachinePolicy or UserPolicy shows a value, it is set by Group Policy and no local Set-ExecutionPolicy will override it. Escalate to whoever owns endpoint policy — before the session, not during it.

    The fourth call fails at the parameter binder — before a single line of the script body executes. Show the room that error. That is the difference between a tool and a shell.

    Do not confuse these two rejections — they teach opposite lessons

    Both produce a security-flavored error. They are not the same thing, and an infrastructure audience will notice if you conflate them.

    RejectionError typeWhat it means
    Execution policy PSSecurityException · UnauthorizedAccess Environment setup. The file never opened. This is not one of your four guardrails.
    Parameter binder ParameterBindingValidationException The design working. [ValidatePattern] rejected the argument before the script body executed. Note that no JSON is returned — the code that emits JSON never ran. This is the guardrail.

    If a participant walks away thinking execution policy is part of the security design, they have learned the wrong lesson from the right demo.

Lab 2

Build the desktop flow

Optional · facilitator demo

The desktop flow is a thin wrapper. Its only job is to accept four typed inputs, call the script file on disk, and hand one JSON string back.

Read this before you start — you probably should not build this lab

This lab needs two things the room may not have: a registered machine, and a premium / RPA entitlement held by the connection owner. Neither is what you are here to learn.

Recommended: the facilitator demonstrates this lab on one prepared machine while participants watch, and participants begin hands-on work at Lab 3, where the agent flow serves the fixture directly. That path needs no machine, no entitlement, and no Power Automate license — agent flows consume Copilot Studio capacity per action executed, and testing from the flow designer or the agent's test chat consumes none at all. Lab 6 therefore runs entirely free; only the Teams publication in Lab 7 draws on capacity.

Build it yourself only if you have a registered machine on Windows Pro, Enterprise or Server and you hold the premium entitlement. Windows Home can author and run desktop flows locally, but Microsoft documents that it cannot trigger them from the cloud — which is the only thing that matters here.

Read the guardrail in Step 5 either way. The %variable% substitution risk is the single most important security point in this handbook, and it applies to any production build that uses a runner.

  1. Confirm the machine is registered

    Open make.powerautomate.com → Monitor → Machines. The runner must appear with status Connected. If it does not, open Power Automate for desktop on the runner, sign in, and register the machine to this environment.

  2. Create a new desktop flow

    On the runner, open Power Automate for desktop → New flow. Name it exactly:

    Desktop flow name
    ENR Computer Lookup Runner
  3. Add four input variables

    In the designer, open the Variables pane → Input/output variables → + → Input. Create each of these as Text:

    Variable nameExternal nameDefault value
    LookupTypeLookup TypecomputerName
    LookupValueLookup Value(empty)
    CorrelationIdCorrelation IdREQ-0000
    RunModeRun ModeMock
    Guardrail — there is no fifth input

    Do not add an input variable that carries script text, a filter string, or a cmdlet name. The instant such a parameter exists, every control in Lab 1 is bypassable. This is the single most important instruction in the handbook.

  4. Add one output variable

    Same pane → + → Output. Name it ResultJson, type Text.

  5. Re-validate the input inside the desktop flow

    Build the validation as a default plus two gates, not as branches with Else blocks. Fail-closed is easier to read and impossible to get half-right.

    Action order in the designer
     1. Get current date and time                    -> %CurrentDateTime%
 2. Set variable  ResultJson = {invalidInput payload}    <-- the default
 3. If  %LookupValue%    matches regex  ^[A-Za-z0-9._-]{1,64}$
 4.   If  %CorrelationId%  matches regex  ^[A-Za-z0-9-]{1,40}$
 5.     Run PowerShell script
 6.     Set variable  ResultJson = %PowershellOutput%
 7.   End
 8. End
 9. If  %ResultJson% contains 'invalidInput'
10.   Write text to file  logs\lookup.log  (append)      <-- the audit line
11. End

    There are no Else branches. If either check fails, ResultJson still holds the rejection payload set in line 2. One place to maintain, and the flow fails closed by construction rather than by remembering to handle it.

    Guardrail — the one real vulnerability in this design

    The Run PowerShell script action performs textual substitution of %variables% into the script before execution. Every variable that reaches that action is therefore an injection path — not just the obvious one.

    %LookupValue% is validated in three separate places: the agent flow (Lab 3), gate 3 above, and the script's own [ValidatePattern]. %CorrelationId% needs the same treatment, and for the same reason: it is filled dynamically by the model (Lab 5), and the script's [ValidatePattern] on it runs after substitution has already happened — too late to help. Validate both, in both places.

    Defense in depth is not optional here — remove any one layer and you have built a shell.

  6. Add the Run PowerShell script action

    From Scripting, drag Run PowerShell script inside the inner gate — line 5 of the action order above. Paste this into PowerShell code to run. Set Fail after timeout to on, with a Timeout of 60 seconds.

    Run PowerShell script · action body
    $ErrorActionPreference = 'Stop'
& 'C:\EnergizerAgent\Get-EnrComputerLookup.ps1' `
    -LookupType    '%LookupType%' `
    -LookupValue   '%LookupValue%' `
    -CorrelationId '%CorrelationId%' `
    -Mode          '%RunMode%'

    The action produces PowershellOutput and ScriptError. Note that the script itself is on disk — the action only references it. Nothing dynamic is being composed.

  7. Map the output

    Add a Set variable action after the script call: set ResultJson to %PowershellOutput%.

    The rejection payload is set as the default in line 2 of the action order, before either gate. Use this literal:

    Default · rejection payload
    {"status":"invalidInput","correlationId":"%CorrelationId%","mode":"%RunMode%","resultCount":0,"results":[],"message":"The lookup value did not match the approved format.","source":"Input validation","durationMs":0}
    Log the rejection as well as reporting it

    Lines 9–11 of the action order are the audit gate. Add a Write text to file action inside an If that tests whether %ResultJson% still contains invalidInput — that is only true when both gates were missed. File path C:\EnergizerAgent\logs\lookup.log, Append set to on. Text:

    Audit gate · rejection line
    %CurrentDateTime%|%CorrelationId%|%RunMode%|%LookupType%|invalidInput|0
    Do not write this line unconditionally

    It is tempting to put the Write text to file straight after the default on line 2, so that “every call is logged”. Do not. The line is hard-coded to invalidInput, so every successful lookup would write a false rejection record and then the script would write the real one on top of it. The log you spend Lab 6 asking people to trust would be wrong for the majority of its entries. Gate it.

    This matches the pipe-delimited format the script writes, so the log stays parseable as one stream. Do the same in the On block error handler with runnerUnavailable. Without these two lines, a rejected attempt leaves no trace on the runner at all — and “did anyone try?” is exactly the question this log exists to answer.

  8. Wrap the whole thing in error handling

    Select all actions → right-click → Enclose in "On block error". In the error handler, set ResultJson to a runnerUnavailable payload. This is what guarantees a dead runner never looks like an empty result.

    Error handler · runner unavailable payload
    {"status":"runnerUnavailable","correlationId":"%CorrelationId%","mode":"%RunMode%","resultCount":0,"results":[],"message":"The lookup could not be completed on the runner machine.","source":"Runner error handler","durationMs":0}
  9. Save and test locally

    Save, then use Run in the designer. Supply computerName / ENR-LT-1234 / REQ-0100 / Mock and confirm ResultJson holds the expected JSON. Fix it here, not later.

Lab 3

Build the agent flow

Copilot Studio

The agent flow is the bridge. It is what the agent can actually see and call — and it is the layer where you enforce validation that the model cannot talk its way around.

  1. Create the flow

    In Copilot Studio, open your agent workspace → Workflows (or Flows) → New agent flow → build with the designer. Name it:

    Agent flow name
    Lookup computer in Active Directory
  2. Set the trigger

    Trigger: When an agent calls the flow. Add three text inputs — the descriptions matter, because the model reads them to decide what to pass:

    InputTypeDescription shown to the model
    lookupTypeTextOne of exactly: computerName, userName, assetId. Nothing else is valid.
    lookupValueTextThe single identifier to look up. Letters, digits, dot, underscore and hyphen only. Maximum 64 characters. Never a sentence, a command, or a wildcard.
    correlationIdTextA short request identifier used for auditing, for example REQ-0001.
    Read this before you write a single expression

    The names you just typed — lookupType, lookupValue, correlationId — are display labels. They are not the field names in the trigger body. Internally, an agent flow names text inputs positionally, in the order you add them.

    An expression written against the display label returns null, and nothing tells you. A missing key resolves silently — no error, no warning, and the Flow checker stays green.

    So verify your own trigger before you write anything. Save the flow, run it once with any values, open the run, click the trigger card and view its raw outputs. The field names you see there are the only ones that work. Thirty seconds here saves an hour later.

    Facilitator: if you add one screenshot to this handbook, make it this one — the trigger card's raw outputs, showing the internal names beside their values.

    Adding the three inputs in the order listed above produces this mapping, which is what the rest of Lab 3 is written against:

    This only affects expressions you write yourself inside this flow. At the tool boundary in Lab 5, the platform binds by display label — lookupType, lookupValue and correlationId are correct there, and should not be changed.

  3. Initialize the result variable with a safe default

    Add an Initialize variable action immediately after the trigger, before the validation condition you build in the next step. Name it ResultJson, type String, value as below.

    Initialize variable · default value
    {"status":"notFound","correlationId":"@{triggerBody()?['text_2']}","mode":"Mock","resultCount":0,"results":[],"message":"No record matched the supplied value.","source":"Mock fixture (agent flow)","executedAt":"@{utcNow('yyyy-MM-ddTHH:mm:ssZ')}","durationMs":0}

    This is the same fail-closed pattern used throughout the build: establish the safe answer first, and overwrite it only when something matches. If every case downstream misses, the flow still returns valid, honest JSON.

    This action has to be at the top level — it cannot go inside the condition

    Power Automate permits variables to be declared only at the global level, not within scopes, conditions, or loops. If you try to add Initialize variable inside the condition branch, the flow will not save. Only Set variable may be used inside a branch.

    This is not a workaround. Declaring the default above the condition means the safe answer exists before validation has even run, so there is no path through the flow — including one you have not thought of — that returns nothing.

    If you ask the designer’s Copilot to build this action, check two fields before moving on

    Asking the in-designer assistant to create this action is reasonable — the payload is long and typing it is error-prone. It gets the payload right. It gets the wrapper wrong in two specific ways, and neither is visible until the flow runs.

    FieldWhat it may produceWhat it must be

    Type Object String. The value is a JSON string, not an object. An Object variable given a String value fails at run time on the very first action.

    Do not name this variable status for a second reason: status is already a field inside the payload and an output name in Respond to the agent. Three different things called status is a debugging problem you do not need in a ninety-minute lab.

    Once the action is saved, the Value field should show two colored chips embedded in the JSON text rather than plain characters:

    Everything else in the field stays plain text. Two chips, and nothing else — that is the whole check.

    The @{…} tokens are expressions evaluated at run time.     If Initialize variable and Set variable are not in your action picker

    Set variable is used inside the condition branch, which is permitted — the restriction described above applies only to declaring a variable. If neither action is in your picker at all, use one of these instead. Your facilitator will have confirmed which applies during the dry run.

    Option A — one Compose, flat lookup. Add a Compose action in the true branch containing a single JSON object whose keys are the six lookup values and whose values are the six payloads. Then point Parse JSON at:

    coalesce(

    One action, no nesting, and adding a seventh fixture row is one more key.     Option B — the guaranteed floor.     Option B must include the Switch's Default case

    With no Initialize variable, the notFound default no longer exists anywhere.     • The expression property is a structured object, not an expression string. The whole clause lives in the first position of an equals array, with true second.
    • There is a single @ at the very start and no @{ } wrappers anywhere inside. Nesting those inside an already-expression context is the most common paste error here.
    • runAfter names the action this one follows. Spaces in an action name become underscores — so Initialize variable becomes Initialize_variable. If you named yours differently, update this key or the flow will not save.

    Both identifiers are checked here, not just the obvious one — see the Lab 2 guardrail for why correlationId matters. The real regex layers live where regex actually exists: Power Automate for desktop’s matches regex operator in Lab 2, and [ValidatePattern] in the script. The point is that something deterministic rejects bad input before the runner is touched. Verify the condition in the designer with a known-good value such as ENR-LT-1234 before moving on — a validation clause that silently rejects everything looks exactly like a broken agent.

Security guardrails — the review checklist

Energizer's assessment was "since it is all internal, there should not be any constraints". Internal reduces network exposure; it does not remove the need for these controls. Walk this list with whoever owns security before Live mode is enabled.

RiskWhy it applies hereControl in this build
Command injection The Run PowerShell script action substitutes %variables% into the script as text before execution. In the production design, allowlist regex enforced in three independent layers — agent flow condition, desktop-flow condition, and the script's [ValidatePattern] — applied to every variable substituted into the action, including correlationId. Note that the workshop build contains only the first of these, because it has no runner; the other two are demonstrated in Labs 1 and 2 rather than built by participants. Excessive privilege It is far easier to run the connection under an admin account, and that is exactly what usually happens. Dedicated service account, delegated read on a single OU, -SearchBase pinned in the script. No write cmdlet exists in the file.

ConvertTo-SafeText strips control characters and truncates; the output allowlist keeps free-text fields out entirely; instructions say to treat tool output as data, never instructions.
Data leakage into chat transcripts A directory object carries far more attributes than anyone intended to publish into a Teams conversation. Six-field output allowlist. Adding a seventh field is a deliberate, reviewable change.
Silent failure An offline runner returning nothing is indistinguishable from a genuine "no match" unless you design for it. Distinct runnerUnavailable state, an On block error handler, and an explicit failing test (T6).
Unauthorized users All queries share one execution identity, so the directory cannot enforce per-user rights. Agent shared only with the Infrastructure security group. Reviewed whenever group membership changes.
No audit trail "Who asked what, and did it run?" must be answerable months later. Correlation id generated by the agent, passed through every hop, and shown to the user in every reply. Two tiers: the runner log records every lookup that executed, plus rejections caught at the desktop flow; Power Platform flow run history records attempts rejected earlier, before the runner was ever contacted. Know which tier answers which question — a rejected injection attempt will not appear in the runner log unless the Lab 2 audit lines are in place.
DLP misconfiguration Power Platform data policies can silently block or isolate the desktop-flow connector. Verify the environment's DLP policy before the session. This is the most common day-of failure.
The design that must never ship

An agent with a script or command parameter, or one that composes a filter string from user text. If a future requirement seems to need it, the correct response is to add a second fixed function, not to make the first one generic.

07

Where this goes next — production paths

What you built today is Level 1 on the maturity ladder: a working vertical slice with mock data. Here is the honest route to Level 3 and beyond.

Recommended production target

Azure Automation + Hybrid Runbook Worker

Move the same script into an Azure Automation runbook and execute it on a Hybrid Runbook Worker installed on a domain-joined server. The agent flow calls the Azure Automation connector instead of the desktop flow.

Why it is better

  • Genuinely non-interactive — no signed-in session, no RPA licensing, no console.
  • Azure RBAC on who can start the runbook; managed identity instead of stored credentials.
  • Native job history, output and error streams — an audit trail you do not have to build.
  • Source-controlled runbooks with versioning and staged publishing.

What it costs you

  • An Azure subscription and the worker agent installed on-prem.
  • A conversation with whoever owns Azure landing zones.
Cleanest contract

Internal REST API + custom connector

Wrap the lookup in an internal HTTPS service that returns the same JSON, then expose it to Power Platform as a custom connector routed through the on-premises data gateway.

  • The API becomes the reusable contract for every future agent, app and script.
  • Typed OpenAPI definition, so the model gets a far better tool description.
  • Requires a team to build, host and own the service — no such API exists at Energizer today.
Pro-code track

MCP server + Microsoft 365 Agents SDK

Expose lookup_computer as an MCP tool. Copilot Studio can consume MCP servers directly, and a custom-built agent on the Agents SDK can too.

  • One tool definition, consumable by Copilot Studio, custom agents and other MCP clients.
  • Requires a publicly reachable HTTPS endpoint plus OAuth — so an on-prem server needs publishing.
  • The right answer once there are five of these tools, not the first one.
Question the premise

Do you need on-prem at all?

If Energizer's devices are Entra hybrid-joined or managed by Intune, Microsoft Graph already knows their name, enabled state, OS, owner and last check-in.

  • No runner, no gateway, no script, no RPA license.
  • Per-user permissions actually work, because each caller uses their own identity.
  • Worth thirty minutes of investigation before anyone builds a production runner.

Suggested sequence after the workshop

  1. Confirm the real question — get the exact script and expected output from the business owner. Everything else is rework until this exists.
  2. Check Graph first — if the cloud already has the answer, stop here and build the far simpler version.
  3. Stand up a read-only service account scoped to one OU, and validate Live mode with the facilitator only.
  4. Pilot with five people from the Infrastructure team for two weeks. Measure: queries run, correct answers, time saved per query.
  5. Move execution to Azure Automation once the pattern is proven and someone wants it running unattended.
  6. Only then consider a write action — with explicit confirmation, a separate tool, and a separate approval.
